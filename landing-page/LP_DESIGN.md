# SdDD LP 設計メモ

## 目的

SdDDを、**AIに読ませる運用ルールとMarkdownテンプレートをセットにした、バイブコーディングのための開発手法**として伝える。訪問者が、要望を書けば何が起き、利用者とAIのどちらが何をするかを最初の画面から理解できることを到達点にする。

## 想定読者

- AIを使って個人開発をしており、要望と実装の対応を確認したい人
- 複数のAIやセッションを使い、仕様とタスクを引き継ぎたい人
- AIと人で開発しており、Issue・PRと仕様書の役割を整理したいチーム

## メッセージの優先順位

1. **何か** — 「SdDD｜AIに読ませる開発手法・運用テンプレート」。開発手法、AI向け運用ルール、Markdownテンプレートをセットで提供する
2. **中核価値** — 要望を書けば、仕様書になり、実装へ進む。要望IDで状態と根拠を追える
3. **体験の違い** — 要望を伝えるだけのバイブコーディングでは仕様が残らない問題と、要望 → 仕様確定 → 仕様書 → 実装・検証というSdDDの順番
4. **利点** — 要望の追跡、仕様と実装の整合、担当交代後の再開
5. **使い方** — 「利用者がすること（1. 要望を伝える、2. 必要な判断に答える）」と「AI・自動化がすること（3. 確定要望を台帳・仕様・タスクへ反映、4. 実装・検証・報告）」を、仕様確定の矢印で分けて表示する。会話で受けた原文はAIが先に記録することも明記する
6. **詳細機能** — ファイルの役割、worktree、GitHub、確認作業の自動化、CodeGraphによる影響範囲確認

## アウトライン

1. **Hero** — タイトルと「要望 → 仕様書 → 実装」の価値を明示し、テンプレートへ誘導
2. **使い方** — 利用者の1・2と、AI・自動化の3・4を仕様確定の矢印で分けた4ステップ
3. **体験の違い** — 通常のバイブコーディング、仕様確定、仕様を基準にした実装・検証の違い
4. **利点** — 要望追跡、仕様と実装の整合、引継ぎの3点
5. **機能** — `requests.md`、`requests_log.md`、`spec/`、`task.md`・`handover/` の役割
6. **拡張運用** — worktree、GitHub Issue / PR、リンク検査・索引・自動化
7. **CodeGraph連携** — SdDDの仕様・受け入れ条件と、CodeGraphの影響範囲確認を分けて使う
8. **開始** — 利用者がするインストーラーによる導入・AIへの指示・要望入力と、その後AIがする仕様化・タスク化・実装・検証を明確に分ける

## 表現とビジュアル方針

- 比喩、抽象表現、効果を断定する言葉は使わず、処理の流れと確認できる情報を具体的に書く。
- 装飾用画像は使わず、要望・仕様・検証が接続される図、番号、ファイル名で仕組みを示す。
- Noto Sans JPと等幅フォントを使い、読みやすさと情報の区別を優先する。
- 重要な図はテキストとしても読めるようにし、色だけに意味を持たせない。
