# 運用自動化と索引

> SdDDのルールを、人の注意力だけに依存させないためのガイド。

## 自動化してよいこと

次のいずれかに当てはまる場合、指揮役は小さなツール・スクリプト・ダッシュボードを提案または作成してよい。

- 同じ転記、確認、検索を二回以上繰り返している
- 要望ID・仕様・タスク・PRのリンク漏れが起きやすい
- 毎回同じ文脈を集め直していて、引継ぎに時間がかかる
- 人間が見やすい進捗表示が必要だが、正本を増やしたくない

作る前に、目的、正本、入力、出力、失敗時の戻し方を短く記録する。

## 境界

- Markdownの要望・仕様・台帳を、許可なく別の正本へ置き換えない
- 外部サービス、課金、認証情報、権限、公開範囲を変えるものは発注者の確認を得る
- 生成物は再作成できるようにする。SQLite索引、HTMLダッシュボード、キャッシュは原則Git管理外にする
- `.sddd/` とCodeGraphの `.codegraph/` は再生成可能なローカルデータとして既定でGit管理外にする。共有が必要な設定・出力だけを、対象・理由・更新者を決めてGit管理する
- ツールが失敗しても、Markdownを手で編集して作業を続けられるようにする

## 推奨する小さな道具

| 道具 | 目的 |
|:--|:--|
| `sddd doctor` | 要望ID、spec、タスク、Issue、PRのリンク漏れを検出 |
| `sddd context R-0001` | 新しいAIへ渡す最小限の仕様・台帳・タスク・引継ぎを集める |
| `sddd handover` | 現在の作業、検証、未解決事項を引継書へ下書きする |
| `sddd index` | MarkdownをSQLiteへ索引化し、要望・状態・影響範囲を検索する |
| `sddd dashboard` | MarkdownまたはIssueから人間向けHTMLを生成する |

## SQLiteの位置づけ

SQLiteは、要望ID・状態・仕様リンクの横断検索や集計が必要になった段階で導入する。最初はMarkdownを正本にし、SQLiteはそこから再生成できる索引にする。

複数Agentが同じタスク状態を高頻度に更新してMarkdown競合が頻発する場合だけ、タスク状態をSQLiteの正本にすることを検討する。その場合は、状態遷移、監査ログ、バックアップ、Markdownへの表示生成を先に設計する。

## HTMLの位置づけ

トップページ、要望一覧、決定事項、進捗はHTMLで見やすくしてよい。ただしHTMLをAIが読む仕様の正本にはしない。Markdownから生成し、AIは `SPEC.md` と必要な詳細だけを読む。

## CodeGraph連携（推奨）

[CodeGraph](https://github.com/colbymchenry/codegraph) は、コードの依存関係と変更影響を調べるローカルのコード索引である。複数モジュールをまたぐ変更、既存コードへの機能追加、並列実装、レビューでは、SdDDと組み合わせることを推奨する。

役割を混ぜないことが重要である。

| 仕組み | 答える問い |
|:--|:--|
| SdDD | 何を変えるか。どの仕様・受け入れ条件を満たすか |
| CodeGraph | どのコード、呼び出し関係、処理経路、テストへ影響するか |

### 実装前の標準手順

1. 要望ID、関係する `spec/`、受け入れ条件を読む
2. CodeGraphで変更箇所の入口、呼び出し元・呼び出し先、影響候補を調べる
3. 実際に変更・確認するファイル、リスク、テスト項目を `task.md`、要望ID別タスク、またはPRへ記録する
4. 実装後は、仕様・受け入れ条件・テスト結果で完了を確認する

CodeGraphの結果は「どこを調べるか」の候補であり、仕様の正本でも完了根拠でもない。小さく独立した変更では必須にせず、影響範囲が読みにくい時に優先して使う。生成データ・ローカル設定・共有範囲を確認し、不要ならいつでも外せる形で導入する。`.codegraph/` は既定でGit管理外とし、導入手順や共有設定だけを必要に応じて文書化する。
