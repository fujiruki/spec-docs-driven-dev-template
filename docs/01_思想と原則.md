# 思想と原則

> 仕様書駆動開発（Spec-docs Driven Development, SdDD）は、要望・仕様・実装の判断を、担当者やAIが交代しても失わないための開発方式である。

## SdDDが守る6つの不変条件

1. **要望を受け止める** — 会話または `requests.md` で受けた要望は、仕様の話を始める前に原文を残し、仕様化を始める時に要望IDを付ける
2. **仕様を現在の正とする** — 現在の振る舞いは `spec/` に書き、コードだけを根拠にしない
3. **経緯を残す** — 仕様確定時に、原文・仕様リンク・受け入れ条件を `requests_log.md` の要望台帳へ移す
4. **実装と検証を結ぶ** — タスク、テスト、手動確認、PRを要望IDに結び、台帳の状態を更新する
5. **交代可能にする** — Agentの会話記憶ではなく、仕様・台帳・タスク・引継書から再開できる
6. **正本を二重化しない** — 要望、仕様、実行進捗、コードレビューにはそれぞれ一つの正本を決める

この6点以外の細かな運用は、必要なときだけ読むモジュールに分ける。ルールを増やして常時読ませないことも、SdDDの重要な設計である。

## 要望から実現まで

```
会話 / requests.md
  │ 生の要望を受け付ける
  ▼
仕様確認
  │ 判断が必要な時だけ発注者へ聞く
  ▼
仕様確定
  ├─ spec/              現在有効な仕様
  ├─ requests_log.md    原文・要望ID・仕様リンク・状態
  └─ task.md / tasks/   実装・検証計画
  ▼
実装・レビュー・検証
  ▼
requests_log.md の同じ記録を完了 / 保留 / 見送り等へ更新
```

`requests.md` は未整理または仕様確認中の入力箱である。仕様が確定した時点で、原文を失わず `requests_log.md` の記録へ移す。`requests_log.md` は終了記録だけではなく、仕様化済み・実装中・完了を追う全要望の台帳である。

## 役割はモデル名ではなく能力で決める

SdDDは、特定のAI、モデル、IDEを前提にしない。指揮、実装、設計助言・レビューという役割を、難度・失敗コスト・利用できる環境に応じて人またはAIへ割り当てる。

`SDDD.md` がツールに依存しない正本ルールである。`CLAUDE.md`、`AGENTS.md`、Claude Code向けコマンド、Codex、CodeGraph、GitHubはすべてアダプターまたは補助機構である。どれかが変わっても、要望IDと文書の関係が残ればSdDDは継続する。

## 要望IDは再利用しない

仕様化を始める要望には `R-0001` 形式の連番を付ける。採番前に `requests.md`、`requests_log.md`、分割済みの要望台帳を確認し、最大番号の次を使う。取り下げ・訂正・他要望への統合でも、既存IDを消したり別の要望へ使い直したりしない。

## ルールを守るために自動化する

同じ転記・確認・検索を繰り返す、または記録漏れの危険がある場合、AIは小さな自動化を提案または作成してよい。自動化は、正本を置き換えず、可逆で、失敗時に手作業へ戻れるものを優先する。

例: 要望IDのリンク検査、引継書の下書き、Markdownからのダッシュボード生成、SQLite索引、コード影響範囲の検索。

外部サービス、課金、認証情報、権限、公開範囲を変える自動化は、発注者の了承なしに実行しない。

## 公開範囲を先に決める

`requests.md` と `requests_log.md` は通常Git管理される。公開または外部共有するリポジトリでは、秘密情報、個人情報、契約上の秘匿情報、生の会話原文を置かない。必要なら、リポジトリには公開可能な要約と安全な保管先への参照だけを残す。
