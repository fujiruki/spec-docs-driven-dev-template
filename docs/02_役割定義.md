# 役割定義

> SdDDは、特定のAIではなく責務を分ける。小規模では一人が兼任しても、成果物の境界は保つ。

## 基本の役割

| 役割 | 担当 | 責務 |
|:--|:--|:--|
| 発注者 | 人間 | 要望を伝え、仕様上の判断と結果を確認する |
| 指揮 | メインのAIまたは人 | 要望の記録、仕様化、台帳化、タスク化、進捗の整合 |
| 実装 | AIまたは人 | 要望ID・仕様・受け入れ条件に従う実装とテスト |
| 設計助言・レビュー | 必要時の独立担当 | 設計の比較、影響範囲、セキュリティ、完了根拠の確認 |
| 統合 | 必要時の担当 | 共有基盤、マージ、リリース、並列変更の整合 |

## 指揮役の最初の責務

発注者が会話で要望を伝えた時、指揮役は「覚えておく」だけでは不十分である。最初に `requests.md` へ原文を記録し、仕様化を始める時に要望IDを付ける。仕様確認を経て確定したら、次を同時に整える。

1. `SDDD.md` の採番規則に従い、`requests_log.md` に原文、ID、仕様リンク、受け入れ条件、状態 `仕様化済み` を記録する
2. `spec/` と `SPEC.md` を更新する
3. 実装・検証タスクを作る
4. 記録を確認してから `requests.md` の該当項目を移動する

指揮役は、実装が終わるまで要望を放置しない。実装担当の報告、検証、PR、発注者の確認に合わせて、台帳の同じ記録を更新する。

## 実装担当

実装担当は、少なくとも次を受け取ってから作業する。

- 要望IDと担当スコープ
- 現行仕様と受け入れ条件
- 変更可能な範囲と依存関係
- タスクと検証方法
- 仕様外の判断が必要になった時の戻し先

仕様の不足を見つけた場合は、実装担当が要望を勝手に完了・見送りにしない。影響と選択肢を指揮役へ返す。

## レビューと統合

認証、権限、課金、個人情報、データ移行、互換性破壊、複雑な設計選択では、実装担当以外の視点で確認する。レビューの結論は、要望IDとともに仕様、変更履歴、PR、引継書のいずれかへ残す。

並列作業では、共有基盤・マージ・リリースの責任を明確に持つ統合担当を置く。全員が同じ仕様書・台帳・設定を同時に編集しない。
