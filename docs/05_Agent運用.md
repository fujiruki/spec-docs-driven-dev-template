# Agent運用

> Agentの会話履歴は加速装置であり、永続記憶ではない。必要な記憶はSdDDの成果物へ残す。

## 実行プロファイル

| プロファイル | 適した場面 | 運用 |
|:--|:--|:--|
| 単独実装 | 小規模変更、並列環境がない | 同じ担当が指揮と実装を兼ねる。仕様・検証・状態更新は分けて確認 |
| worktree並列 | 独立した複数機能 | 1要望ID / 1ブランチ / 1worktree / 1実装担当 |
| 専門家レビュー併用 | 高リスク・難しい設計 | 実装前または統合前に独立した助言・レビューを入れる |
| GitHub協業 | 複数人の担当・レビュー | Issue、PR、保護ブランチで作業と統合を追う |

モデル・Agent数は固定しない。作業の独立性、失敗コスト、利用可能な能力で選ぶ。

## 分割の原則

機能で分ける。フロント、バック、API、DB、テストを一つの機能に必要な範囲で同じ担当が持つ。

同じコードファイル、DBマイグレーション、共有設定、認証、共通UI基盤を変える作業は競合しやすい。並列に開始せず、統合担当を決めるか順序を付ける。

## 引継ぎとコンテキスト健全性

次のいずれかが起きたら、引継ぎまたは独立レビューを提案する。

- 同じ失敗、見落とし、場当たり的な修正を繰り返す
- 指示、仕様、要望ID、検証条件を漏らす
- 関係ないファイルへ変更が広がる
- 重要な設計判断をした
- セッションを替える、または長時間の作業へ入る

引継書には次を残す。

- 要望ID、担当スコープ、ブランチ、worktree、基準コミットSHA
- 完了・未完了タスク、未コミット変更、実施済みテスト
- 設計判断、既知の問題、発注者またはレビュー担当への質問
- 次の担当が最初にする確認と検証

新担当は、先に `SDDD.md` を読み、関係する仕様、要望台帳、タスク、引継書を読んでから、理解したスコープと次の検証を報告して再開する。

## 進捗を正確にする

実装担当の「できました」は完了根拠ではない。指揮役は、要望IDに対して受け入れ条件、テスト・手動確認、レビュー、残るリスクを確認し、`requests_log.md` の状態を更新する。

詳しいworktree・GitHub運用は [並列・協業開発](09_並列・協業開発.md) を、自動化・SQLite索引は [運用自動化と索引](08_運用自動化と索引.md) を参照する。
