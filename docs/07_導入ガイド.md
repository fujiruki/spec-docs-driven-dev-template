# 導入ガイド

> SdDDは、AIに読ませる共通ルール `SDDD.md` と、要望・仕様・タスクのMarkdownテンプレートをプロジェクトへ入れて使う開発手法である。

## 推奨: インストーラーで導入する

SdDDの参照リポジトリを取得し、導入先のプロジェクトを指定する。導入先は空の新規プロジェクトでも、既存のGitリポジトリでもよい。インストーラーは既存の同名ファイルを既定で上書きしない。

PowerShell:

```powershell
git clone https://github.com/fujiruki/spec-docs-driven-dev-template.git
cd spec-docs-driven-dev-template
.\scripts\install-sddd.ps1 -ProjectPath 'C:\Projects\my-app'
```

GitHubのIssue/PRテンプレートも使う場合:

```powershell
.\scripts\install-sddd.ps1 -ProjectPath 'C:\Projects\my-app' -WithGitHub
```

macOS/Linux:

```sh
git clone https://github.com/fujiruki/spec-docs-driven-dev-template.git
cd spec-docs-driven-dev-template
./scripts/install-sddd.sh /path/to/my-app --with-github
```

Claude Code用のアダプターとコマンドが不要な環境では、`-WithoutClaude` または `--without-claude` を付ける。既存ファイルを更新したい時だけ、差分とバックアップ方針を確認してから `-Overwrite` または `--overwrite` を使う。

## 導入されるもの

最小限の正本は次である。

```text
SDDD.md                 <- ツールに依存しない運用規則
AGENTS.md               <- 汎用AI向けアダプター
docs/SPEC.md            <- 現在の仕様への入口
docs/requests.md        <- 未整理・仕様確認中の要望
docs/requests_log.md    <- 仕様確定後の全要望台帳
docs/spec/              <- 現在有効な仕様
docs/handover/          <- 担当交代時の再開記録
task.md                 <- 実装・検証計画
```

Claude Codeを使う場合は、これに `CLAUDE.md` と `.claude/commands/` が加わる。これらは `SDDD.md` を読むためのアダプターであり、ルールの正本ではない。

Codexを使う場合は、`.agents/skills/kaigi/` と `.agents/skills/kaigi2/` も導入される。Codexの明示呼び出しは `$kaigi` / `$kaigi2`、Claude Codeの対応するコマンドは `/kaigi` / `/kaigi2` である。`kaigi` は単一コンテキストの軽量版、`kaigi2` は独立Agentによる高品質版として使い分ける。

`docs/automation.md`、`docs/collaboration.md`、GitHubのIssue/PRテンプレートは、必要になった時に使う任意モジュールである。`.sddd/` と `.codegraph/` はローカルの再生成可能な補助データとして `.gitignore` に加わる。

## 最初の要望から実装まで

利用者は、要望を `docs/requests.md` に書くか、指揮役AIへ伝える。AIは次の順で進める。

1. 会話で受けた要望も、仕様の話を始める前に `requests.md` へ原文で記録する
2. 仕様化を開始する時に、`SDDD.md` の規則で `R-0001` 形式のIDを採番する
3. 判断が必要な点だけ利用者へ聞き、仕様を固める
4. 仕様が確定したら、同じR-IDで `requests_log.md`、`spec/`、`SPEC.md`、タスクを更新し、受け入れ条件を残す
5. 記録を確認してから、その入力だけを `requests.md` から取り除く
6. 実装・検証・レビューの結果を、同じ要望台帳の状態と根拠に追記する

`requests.md` は入力箱、`requests_log.md` は仕様確定後の全要望台帳、`spec/` は現在の正である。実装担当は入力箱ではなく、対象R-IDの台帳・仕様・タスクを読む。

## 既存プロジェクトへ入れる時

既存のREADMEや設計資料を一度に書き換えない。最初に `docs/SPEC.md` から既存資料へリンクし、次の新しい要望からSdDDの台帳運用を始める。

旧 `docs/request_log.md` がある場合は、内容を変えずに `docs/requests_log.md` へ名称移行する。旧ログが完了記録だけなら、過去の状態を捏造して台帳へ変換しない。以後に仕様確定する要望から新しい形式を使う。

GitHub Templateで空のリポジトリを作ること自体は可能だが、参照リポジトリのルートは配布用の構成を含む。利用するプロジェクトには、必ずこのインストーラーで `templates/` の内容を展開する。

## 段階的な拡張

| 困りごと | 追加するもの |
|:--|:--|
| 要望や台帳が大きくなった | 要望IDごとの詳細ファイル、SQLite索引 |
| 人間が進捗を見づらい | Markdownから生成するHTMLダッシュボード |
| 同じ確認を繰り返す | リンク検査、コンテキストパック、引継書生成 |
| 独立した機能を同時に作りたい | worktree、要望ID別ブランチ、要望ID別タスク |
| 複数人で担当・レビューしたい | GitHub Issue、PR、保護ブランチ |
| 影響範囲が読みにくい | CodeGraphによるローカルのコード索引 |

拡張は、Markdownの正本を置き換えず、必要性が見えた時だけ足す。

## 公開・共有するとき

`requests.md` と `requests_log.md` は通常Git管理される。公開または外部共有するリポジトリには、パスワード、トークン、秘密鍵、個人情報、契約上の秘匿情報、生の会話原文を記録しない。必要なら、安全な保管先を参照する公開可能な要約だけを残す。

## よくある疑問

### Q: requests.md と requests_log.md の違いは？

`requests.md` は仕様化前の入力箱。`requests_log.md` は仕様確定後の全要望台帳。実装中・完了・見送りも後者で状態を更新する。

### Q: Issueを使えば requests_log.md は不要？

不要にはならない。Issueはチームの担当・議論・PR連携、要望台帳は原文・仕様・経緯をプロジェクト内で守るためのもの。公開できない情報もあるため、役割を分ける。

### Q: SQLiteは最初から必要？

不要。最初はMarkdownを正本にし、横断検索・集計・並列状態更新が重くなった段階で、再生成できる索引として導入する。

### Q: 特定のAIやモデルが必要？

不要。どのAIでも `SDDD.md` を読めば使える。Claude Code、Codex、CodeGraph、GitHubは環境ごとのアダプターまたは補助機構である。
