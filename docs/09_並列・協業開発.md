# 並列・協業開発

> worktree、複数Agent、GitHubを使い、同じ要望を安全に並列で実現する。

## 実行プロファイル

| プロファイル | 向く場面 | 基本単位 |
|:--|:--|:--|
| 単独実装 | 小規模変更 | 要望IDと1ブランチ |
| 並列Agent | 独立した機能を同時に進める | 1要望ID / 1 worktree / 1ブランチ |
| チーム協業 | 複数人が担当・レビューする | 1要望ID / 1 Issue / 原則1 PR |

## worktreeと並列Agent

Git worktreeを使うと、一つのリポジトリで複数ブランチを別フォルダへ同時にチェックアウトできる。仕様が確定したR-0012は、`feat/r-0012-機能名` ブランチと専用worktreeを作り、そのAgentだけが実装する。

並列にしてよいのは、仕様・変更範囲・受け入れ条件が独立している作業だけである。次は一人の統合担当を決めるか、順番に行う。

- 同じコードファイルや同じDBマイグレーションを変更する
- 共有設定、依存関係、認証、共通UI基盤を変える
- 片方の実装がもう片方のAPI・型・データ構造を前提にする

### 所有権

| 成果物 | 更新者 |
|:--|:--|
| `requests.md`、`requests_log.md`、`spec/` | 指揮役または明示された文書担当 |
| 要望ID別のコード・テスト | その要望の実装担当 |
| 共有基盤・統合・マージ | 統合担当 |
| 引継書 | 現在の実装担当 |

Agentは仕様の不足を見つけても、共通の正本を独断で変更しない。要望ID、判断が必要な点、影響範囲を指揮役へ返す。

## 引継ぎとコンテキスト健全性

Agentの劣化や幻覚を完全に予測することはできない。代わりに、次の時点で引継書またはチェックポイントを作る。

- 重要な仕様・設計判断をした後
- 一定数のサブタスクを終えた後
- 同じ失敗・見落とし・場当たり的修正が繰り返された時
- セッションを替える前、または長時間作業を続ける前

引継書には、要望ID、ブランチ、worktree、コミットSHA、未コミット変更、読んだ仕様、実施したテスト、既知の問題、次の一手を書く。新しい担当は、それらを読み、最初に理解したスコープと検証方法を報告してから作業を再開する。

## GitHubでの協業

GitHub Issueは、発注者の生の要望を入れる場所ではない。仕様確定後にチームが着手する作業単位として使う。

| 情報 | 正本 |
|:--|:--|
| 生の要望 | `requests.md` |
| 原文・仕様リンク・状態・結末 | `requests_log.md` |
| 現行仕様 | `spec/` |
| 担当・議論・ブロッカー | GitHub Issue |
| 差分・CI・レビュー・マージ | Pull Request |

Issue本文には、要望ID、仕様リンク、受け入れ条件、担当、実装タスクを置く。PRタイトル・説明には要望IDを含め、`Closes #123` でIssueと結ぶ。PRには仕様リンク、受け入れ条件、検証結果、影響範囲、未解決事項を記載する。

### チームの最小ルール

1. 原則として1要望IDにつき1 Issue、1実装PRにする
2. `main` への直接pushを禁止し、PR・CI・必要なレビューを通す
3. Issueの状態は担当・議論のため、仕様の正本にはしない
4. GitHub Projectは人間向けの進捗一覧として任意で使い、台帳や仕様と二重入力しない
5. 顧客情報・未公開戦略・生の会話を公開Issueへ転記しない。必要なら要約・非公開Issue・別の安全な場所を使う

`requests.md` と `requests_log.md` もGit管理される前提で扱う。パスワード、トークン、秘密鍵、個人情報、契約上の秘匿情報、公開できない会話原文は書かず、安全な保管先への参照と公開可能な要約に置き換える。

保護ブランチでは、PR、承認、ステータスチェックをマージ条件として設定する。レビュー指摘を受けた時は、修正・再検証・回答をPR上に残す。
