# ワークフロー

> 要望を受けてから、仕様・タスク・実装・検証・結末を一つの要望IDで追う。

## Phase 1: 受付

要望の入力は `requests.md` または会話で受ける。会話で受けた場合、指揮役は仕様の話を始める前に `requests.md` へ原文を追記する。

仕様化を開始する要望には、`SDDD.md` の採番規則で `R-0001` のようなIDを付ける。似た要望があれば、他要望への統合候補として発注者へ示すが、勝手に消さない。

## Phase 2: 仕様詰め

要望を実現可能な仕様へ変換する。曖昧さ・優先順位・利用者への影響・選択肢がある時だけ、発注者に具体的に確認する。確認事項が残る間、要望は `requests.md` にある。

## Phase 3: 仕様確定・台帳化・タスク化

仕様が固まったら、次を一つのまとまりとして行う。

1. `requests_log.md` に原文、要望ID、受付日、状態 `仕様化済み`、仕様リンク、受け入れ条件を追記する
2. 関係する `spec/*.md` と `SPEC.md` を更新し、要望IDを記す
3. 既存仕様を変えた場合は `spec/06_変更履歴.md` に要望IDと理由を記す
4. `task.md` または `tasks/R-0001.md` に、実装・テスト・手動確認・レビューのタスクを作る
5. 記録漏れがないことを確認し、`requests.md` から該当項目だけを削除する

この時点で、実装がまだでも要望は `requests_log.md` から追える。実装担当は `requests.md` ではなく、仕様と対象要望IDの台帳記録を読む。

## Phase 4: 実装・検証

実装担当には、要望ID、関係する仕様、受け入れ条件、変更可能な範囲、タスク、検証方法を渡す。

- 実装開始時: 台帳を `実装中` にする
- 仕様外の判断が必要: Phase 2へ戻す
- テスト・手動確認: タスクへ結果を記録する
- 完了報告: 変更内容だけでなく、要望を満たす根拠・残るリスク・未実施事項を含める

## Phase 5: レビュー・結果確認

指揮役または独立レビュー役は、仕様、受け入れ条件、検証結果、影響範囲を確認する。発注者の確認が必要なプロジェクトでは、結果を示して確認を得る。

`requests_log.md` の同じ記録を、`検証中`、`完了`、`保留`、`見送り`、`取り下げ`、`他要望へ統合` のいずれかへ更新し、理由・確認日・PR/コミット・関連要望を残す。`他要望へ統合` の場合は、統合先R-IDと理由を残す。コードのマージは `完了` の根拠として扱い、状態名と混同しない。

## Phase 6: 統合・デプロイ

プロジェクトの承認ルールに従ってマージ・デプロイする。チームではPRと保護ブランチを使い、要望ID・Issue・PR・検証を結ぶ。マージが完了して初めて `完了` とするプロジェクトでは、Phase 5の状態更新をマージ後に行う。

## セッション開始時

1. `SPEC.md` を読む
2. `requests.md` の未整理要望を確認する
3. `requests_log.md` から `仕様化済み`、`実装中`、`検証中`、`保留` の要望を短く確認する
4. `task.md`、`tasks/`、`handover/` から続きの作業を確認する
5. 今回の要望IDに関係する仕様だけを選択して読む

過去の完了・見送り記録は、類似要望や判断理由を確認する時だけ開く。
